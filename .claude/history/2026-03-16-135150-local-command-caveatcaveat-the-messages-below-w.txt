⏺ The referee agent currently has no connection to the Random::Engine at all —
  it's entirely absent from the agent's code and from Runner. The random engine
  exists as a standalone object but nothing instantiates or calls it.

  The gap matters most in a few scenarios:
  - Setup: shuffling the 40-card deck and dealing 8 stacks of 5
  - Training: dealing cards into stacks, determining first player
  - Duel: the initiate_attack tie-break (your edge case now uses a die roll)

  How the wiring would need to work:

  The referee is purely an LLM judge — it validates actions and returns
  state_changes. It can't call Ruby methods. The Runner is the host process that
   actually executes state changes. So the right home for random calls is
  Runner, not RefereeAgent.

  The current flow is:
  Runner#play_turn → agent.take_turn → referee.validate →
  game_state.apply_changes

  The state_changes hash the referee returns is passed directly to
  apply_changes. If a state change requires randomness (e.g., "shuffle and deal
  the deck"), the referee can signal that randomness is needed in its response,
  but the actual call to Random::Engine has to happen back in Runner.

  Concretely, two approaches:

  1. Extend state_changes with a random_ops key — the referee includes entries
  like {"op": "shuffle", "target": "deck"} in its response, and Runner
  intercepts these, calls Random::Engine, and applies the results before passing
   the rest of the state changes through. The referee never touches randomness
  directly.
  2. Runner handles known random-triggering actions pre-emptively — certain
  action types (e.g., select_training_stack) are flagged in the rules, and
  Runner resolves the random component (shuffle, deal) before calling the
  referee at all, injecting the resolved values into the game state.

  Option 1 is more general; option 2 is simpler but requires baking knowledge of
   which actions need randomness into Runner. Given that the rules are supposed
  to be data-driven, option 1 fits the architecture better — though it requires
  Runner to interpret the random_ops array and RefereeAgent's system prompt to
  be taught the random_ops vocabulary.

  Right now neither approach is implemented — Random::Engine is genuinely
  orphaned.

⏺ Both issues have the same root cause: Runner is currently a thin loop that
  hands everything to the LLM agents, when it should be the authoritative
  executor for deterministic mechanical operations.

  Random::Engine

  Runner should own a Random::Engine instance and use it in two places:

  1. Before the game loop — a setup phase that Runner runs directly: shuffle the
   40-card deck, deal 8 stacks of 5, assign first player. The LLMs don't need to
   be involved in this at all; it's mechanical.
  2. In-game tie-breaks — when the referee's state_changes response signals that
   a random resolution is needed (e.g., the simultaneous EI! die roll in your
  edge case). The cleanest way is a random_ops array in the referee's response
  schema:
  { "valid": true, "state_changes": {...}, "random_ops": [{"op": "roll",
  "sides": 6, "for": "ei_tiebreak"}] }
  2. Runner intercepts these, calls Random::Engine, resolves the results, and
  either feeds them back into the state or uses them to pick a winner. The
  referee's system prompt needs to be taught this vocabulary.

  Stance pile ordering

  The agents should not manage pile ordering — that belongs in Runner and the
  state representation. The key issues:

  - The game state currently stores stance piles as flat arrays in custom. The
  convention for which end is "top" vs "bottom" is unspecified.
  - Runner needs to enforce context-sensitive draw direction: hand maintenance
  draws from the bottom of a stance pile; storing goes to the top; tucking goes
  to the bottom.
  - PlayerAgent currently gets the raw game state JSON. It should receive its
  own piles in full (it can privately look at them), but the opponent's piles
  should be filtered to top card only before being passed in. Otherwise the
  player agent has perfect information it shouldn't have.

  The agent's job is just to declare intent: "draw from my middle stance pile."
  Runner pops from the correct end based on which operation is in play — the
  player agent and referee don't need to specify the index. The referee
  validates legality (is there a card there? is this draw legal right now?);
  Runner executes the actual array mutation.

  So the changes needed are:
  1. Runner gains a Random::Engine and a setup method called before the game
  loop
  2. Runner gains a state-view filter that sanitizes opponent stance piles to
  top-card-only before passing to PlayerAgent
  3. Runner interprets random_ops from referee responses
  4. The state_changes contract is extended with random_ops
  5. RefereeAgent's system prompt is updated to teach this vocabulary

⏺ Correct on both counts. Here's how it fits together:

  The filtered view

  GameState needs two serialization paths:
  - to_h — full fidelity, used for checkpoints, transcripts, and the referee
  (who is the impartial judge and should see everything)
  - to_h_for(player_name) — the agent-visible view, where the opponent's stance
  piles are reduced to { element: <top_card_element>, depth: <count> } per
  position, plus their sword token position. The receiving player sees their own
   piles in full.

  Runner then uses to_h_for(player_name) when calling agent.take_turn and to_h
  when calling referee.validate.

  The internal state concern

  GameState already holds the object internally — @game_state in Runner is the
  live instance. The problem is apply_changes: it uses merge! on @custom, which
  for stance piles (arrays) would replace the entire pile array rather than
  applying a targeted operation. So if the referee returns state_changes: { 
  "custom": { "Player 1_stance_high": [...] } }, it works only if the referee is
   returning the complete new array. That's acceptable since the referee has
  full state, but it means the referee needs to correctly reconstruct the pile
  after every operation (pop from bottom, push to top, tuck, etc.) — which is
  asking a lot of an LLM doing state_changes in one shot.

  A safer approach: keep apply_changes for scalar values (flags, scores, simple
  custom fields), and add discrete methods to GameState for pile mutations —
  draw_from_stance(player, position), store_to_stance(player, position, card),
  tuck_to_stance(player, position, card) — that Runner calls directly after
  interpreting the referee's validated intent. The referee then returns what 
  happened (e.g., "draw_from: stance_high") rather than the resulting array
  state, and Runner executes it against the real object.

  That keeps GameState as the authoritative source of truth with clean, tested
  operations, rather than relying on the LLM to reconstruct array state
  correctly.

⏺ Yes, that's a clean architectural direction. The shape of it:

  The gem (testr-core or similar) provides:
  - Testr::State::Base — shared serialization interface with to_h (full/private)
   and to_public_h (filtered)
  - Testr::State::GameState < Base — turn tracking, current player, phase, win
  condition evaluation
  - Testr::State::PlayerState < Base — hand, player flags, score; to_public_h
  exposes only what opponents should see
  - Testr::Session::Runner, Manager, Reporter — game-agnostic
  - Testr::Agents::RefereeAgent, PlayerAgent — base prompt logic
  - Testr::Random::Engine — as-is

  The game implementation (testr-shinken or just your game project) provides:
  - Shinken::State::GameState < Testr::State::GameState — discard pile,
  aggressor token, training stacks, phase
  - Shinken::State::PlayerState < Testr::State::PlayerState — the 5 stance piles
   as ordered arrays, sword position, pile operations (draw_from_stance,
  store_to_stance, tuck_to_stance); to_public_h returns top card element + depth
   per position + sword position
  - Optionally subclassed agents if the prompt needs game-specific shaping

  The key boundary is: anything the framework needs to call on state objects is 
  defined in the base classes as an interface; anything game-specific is in the 
  subclass. The Runner calls player_state.to_public_h without knowing it's
  Shinken — the subclass handles what "public" means for that game.

  One naming note: since public/private carry weight in Ruby, to_h (full) and
  to_public_h (filtered) works, or serialize / serialize_for(observer) if you
  want the observer identity to influence the output (which you might — a
  referee vs. a player might get different views).

  The main tension point to anticipate: the Runner currently calls
  game_state.apply_changes(hash) with a flat diff from the referee. Once you
  have PlayerState objects with real behavior, you'll want the runner to call
  discrete state methods rather than merging hashes — which means the referee's
  response contract shifts from "here's the new state" to "here's what
  happened," and the runner interprets that into method calls. That's a more
  robust design but requires the referee's prompt to speak a defined vocabulary
  of state-change intents.
