  ---
  Proposed Architecture

  Directory structure

  testr/
    bin/
      testr              # CLI entry point (start, resume, stop)
    lib/
      testr/
        compiler/        # Markdown rules → structured JSON
        session/         # Session lifecycle, SIGINT handling, state persistence
        state/           # Game state manager (turn tracking, tokens, scores)
        agents/          # Ollama HTTP client, player + referee agent roles
        random/          # Random engine (dice, shuffles, draws)
        reporter/        # Markdown report + transcript generation
    rules/               # Compiled rules files live here
    sessions/            # Per-session JSON state + turn transcripts
    reports/             # Final markdown reports
    spec/

  Roles

  - Orchestrator — drives the game loop, routes messages, triggers saves,
  handles interrupts
  - Player agents (N instances) — take turns, reason about game state, propose
  actions
  - Referee agent — validates proposed actions against the rules; resolves
  ambiguity

  Communication

  Each turn is a JSON envelope:

  {
    "turn": 4,
    "player": "agent_1",
    "game_state": { ... },
    "action": { "type": "play_card", "card": "..." },
    "reasoning": "..."
  }

  Referee receives the action + current state and returns valid: true/false +
  explanation. If invalid, the player is asked to try again (with a retry cap to
   avoid loops).

  Resumability

  State saved to sessions/<id>/state.json after every validated turn. On
  crash/interrupt, bin/testr resume <session_id> reloads from the last
  checkpoint. SIGINT triggers a clean save before exit.

  Model recommendation

  ┌─────────┬────────────────────────┬───────────────────────────────────────┐
  │  Role   │         Model          │                  Why                  │
  ├─────────┼────────────────────────┼───────────────────────────────────────┤
  │ Players │ llama3.2:3b            │ Fast, ~2GB each, no GPU required      │
  ├─────────┼────────────────────────┼───────────────────────────────────────┤
  │ Referee │ qwen3:8b or mistral:7b │ Better reasoning for rules validation │
  └─────────┴────────────────────────┴───────────────────────────────────────┘

  With 32GB RAM this runs comfortably. The RTX 3050 (8GB VRAM) can offload the
  referee model layers — Ollama handles this automatically.

  Rules compiler

  Markdown rules → structured JSON with explicit sections: setup,
  turn_structure, actions[], win_conditions, edge_cases[]. You write markdown;
  the compiler produces the JSON the agents consume. You can also hand-edit the
  JSON directly if needed.

⏺ Yes, and honestly I'd recommend involving me (or a capable cloud LLM) for this
   step rather than the local model. Here's why: rule compilation is the
  highest-stakes semantic work in the whole pipeline — a misinterpreted edge
  case or ambiguous action definition will silently corrupt every test session
  that uses it. A 3-8B local model will likely get the structure right but
  fumble the nuance.

  The practical split I'd suggest:

  - Script's job: parse your markdown rules doc structurally (extract headings,
  lists, tables) into a skeleton JSON, validate the output against the schema,
  and save it to rules/
  - Your job / my job: fill in the semantic gaps — interpreting intent,
  clarifying edge cases, writing the edge_cases[] array that the referee will
  actually consult

  Since you only compile rules occasionally (new game, new version), the cloud
  cost is negligible — a single Claude call per ruleset.

❯ OK one thing I'm not seeing here -- what is receiving the `/api/chat/` POST

⏺ Ollama is the server. It's a local HTTP server that wraps LLM inference —
  OllamaClient just POSTs to it.

  The full chain:

  bin/testr
    └── Session::Runner
          ├── PlayerAgent  ──┐
          ├── PlayerAgent  ──┼──► OllamaClient
          └── RefereeAgent ──┘         │
                                       │  POST /api/chat
                                       │  { model: "llama3.2:3b", messages:
  [...] }
                                       ▼
                                Ollama HTTP server
                                (localhost:11434)
                                       │
                                loads model into memory,
                                runs inference on GPU/CPU
                                       │
                                returns { message: { content: "..." } }

  For this to work you need:

  1. Ollama running on the target machine — either as a background service or
  via ollama serve. It listens on localhost:11434 by default.
  2. Models pulled on that machine:
  ollama pull llama3.2:3b
  ollama pull qwen3:8b
  3. If Ollama is on a separate machine (e.g. your gaming PC), you need to tell
  Ollama to listen on all interfaces — set this in Ollama's environment before
  starting it:
  OLLAMA_HOST=0.0.0.0 ollama serve
  3. Then point TESTR at it:
  TESTR_OLLAMA_HOST=192.168.1.x bundle exec bin/testr start rules/my_game.json

  3. If you're running TESTR on the same machine as Ollama, the default
  localhost works and no extra configuration is needed.

  You can verify Ollama is reachable before starting a session with:
  curl http://<host>:11434/api/tags
  That returns the list of pulled models — if it responds, TESTR can talk to it.

❯ Among the agents in @lib/testr/agents/ I see they also use `JSON.parse` for   
the response body, but it doesn't look like anything is being saved to any      
files. How does the session get recorded so that it can be reported later?      
  ⎿  Listed directory lib/testr/agents/

⏺ The agents don't record anything — that's intentional. The JSON.parse in the
  agents is just deserializing the LLM's HTTP response into a Ruby hash to
  return to the caller.

  The recording happens in Runner and Manager:

  1. After each valid turn, Runner#play_turn calls
  @manager.append_transcript_entry(entry) — this writes one JSON object per line
   to sessions/<id>/transcript.jsonl
  2. After each turn (valid or not), Runner#play_turn calls
  save_checkpoint('in_progress') — this overwrites sessions/<id>/state.json with
   the full current game state and turn log
  3. At game end (or interrupt), Runner#run calls generate_report — this reads
  from @turn_log (the in-memory accumulation of all turn entries) and writes
  reports/<id>.md

  So the data flow is:

  OllamaClient → PlayerAgent → Runner (records via Manager) → sessions/<id>/
                                                             ↓
  RefereeAgent ──────────────────────────────────────────── transcript.jsonl
  (one line per turn)
                                                             state.json
  (full checkpoint, updated each turn)

                                            at game end → reports/<id>.md

  The report CLI command and Runner.resume both read from state.json to
  reconstruct state — transcript.jsonl is the raw turn-by-turn record for your
  own review.
