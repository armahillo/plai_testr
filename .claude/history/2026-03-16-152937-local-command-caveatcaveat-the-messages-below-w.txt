⏺ Here's the complete picture:

  1. Is PlayerState where draw/look operations are defined?

  No — PlayerState is a data container. "Draw a card" would be expressed as an
  action type in the rules JSON, and the referee returns state_changes that move
   card data from e.g. custom['deck'] into the player's player_states[name]. The
   subclasses of GameState/PlayerState define the structure of that data, not
  the behavior.

  2. Multi-step action (draw + decide) — single round-trip or multiple passes?

  Currently single round-trip only. The referee gets a proposed action and
  returns state changes. There's no mechanism to say "first reveal these cards
  to the player, then ask them to choose." That requires an intermediate state
  re-serialization and a second player query before advancing the turn.

  3. Two actions per turn — does it work as-written?

  No. play_turn does exactly one attempt_turn cycle, applies changes, then calls
   advance_turn. It doesn't loop. The turn_structure phases are in the rules
  JSON (used in the player's system prompt for flavor) but Runner#play_turn
  never iterates over them.

  ---
  The gap: turn_structure is already a first-class concept in the rules format,
  but Runner ignores it operationally. The fix would be refactoring play_turn to
   loop through phases, calling attempt_turn per phase before advancing the
  turn. Each phase would pass the current (possibly updated) game state to the
  player, so information revealed in phase 1 (e.g. drawn cards) is visible when
  phase 2 is prompted.

  Whether that's worth doing now depends on whether your target games actually
  need it — if phases are sequential and each phase maps cleanly to one action,
  the loop is straightforward. If a phase can produce a variable number of
  sub-decisions (look at N cards, keep one), it gets more complex.

⏺ This implies several architectural changes. Let me map them out:

  play_turn becomes a loop

  Instead of one action → advance turn, the runner loops asking the active
  player for actions until they declare end_turn. Turn advancement only happens
  after that signal.

  end_turn as a first-class action

  Always available to the active player, no referee validation needed — it's
  just a signal to break the loop.

  Reaction pass after each action

  After the active player's action is validated and applied, the runner queries
  each other player in order with the triggering action and that player's
  available reaction actions. Default is a no_op. Reactions are also validated
  by the referee and state changes applied before the active player continues.

  Rules format additions needed:
  - Actions tagged with triggers_reactions: true (attacks)
  - Actions tagged with reaction: true (reactions, only available in response to
   attacks)
  - Possibly responds_to: ["attack"] to constrain which reactions are valid
  against which triggers

  PlayerAgent needs a second interface

  take_turn is for the active player. A react_to(triggering_action, game_state, 
  available_reactions) method handles the interrupt prompt — framed differently
  ("Player X is playing an attack. Do you have a reaction?") with a no_op as the
   default/fallback.

  ---
  The flow per turn would look like:

  loop:
    active player → action
    if end_turn → break
    referee validates
    apply state changes
    if action triggers_reactions:
      for each other player:
        player → reaction or no_op
        referee validates reaction (if not no_op)
        apply reaction state changes
    log action + any reactions as sub-entries
  advance turn

⏺ Two other minor things to be aware of, but not necessarily worth changing now:

  1. Reactions have no retry logic. If react_to returns an invalid action, it's
  silently skipped (state changes not applied) but still recorded in the log.
  Since no_op is always valid, a stall here is unlikely. If you want parity with
   attempt_turn, you'd need a similar retry loop around reactions.
  2. Referee has no reaction context. When validating a reaction, the referee
  just sees player, action, game_state — it doesn't know what it's reacting to.
  For games where legality of the reaction depends on what triggered it (e.g.,
  "Moat only blocks attacks"), the triggering action would need to be passed
  through to validate. The referee could infer from game state in simple cases,
  but this is worth keeping in mind when writing your rules document.

⏺ Here's a full assessment organized by severity:

  ---
  Blocking for a real first run

  The setup hook is a no-op and nothing executes the setup steps in the rules
  JSON. For any card game, hands are never dealt and the deck is never
  populated, so agents would start with no state to act on. This requires either
   a concrete implementation in a game-specific Runner subclass, or a built-in
  mechanism for executing setup steps against @random and @game_state. This is
  the only thing that would prevent a run from going anywhere.

  Related: example.json stores hands in custom with keys like "Player 1_hand"
  rather than in player_states[name]['hand']. That structure doesn't align with
  how PlayerState serializes — it would confuse both the agents and
  apply_changes. The example needs to be updated alongside whatever setup
  solution you choose.

  ---
  Code issues to fix now

  - attempt_reaction tracks an attempts array that's never used — it was copied
  from attempt_turn but there's no StalledError path to pass it to. Dead code.
  - Runner.resume calls JSON.parse(File.read(...)) directly instead of
  RulesLoader.load(...), bypassing schema validation on resume.

  ---
  Schema/documentation debt

  - schema.json doesn't document triggers_reactions or reaction on action items
  — those fields were added to the runner but never reflected in the schema.
  RulesLoader won't warn if they're missing or misspelled.
  - RulesLoader references SCHEMA_PATH but the validate method doesn't actually
  use it — validation is just a manual required-key check. If you want proper
  JSON Schema validation, that would need a gem like json_schemer.

  ---
  No tests for the core execution path

  Runner, PlayerAgent, and RefereeAgent have no specs. The state layer and
  manager are tested. The agent specs require mocking Ollama which is
  straightforward but hasn't been done. Given how much logic now lives in Runner
   (reaction pass, retry loops, mid-turn game-over), that's the highest-risk
  untested area.

  ---
  Known/deferred (already in TODO)

  - available_actions isn't context-filtered (referee handles legality, so this
  is a quality-of-life issue, not a correctness one)
  - apply_changes uses merge! which replaces arrays wholesale — fine for simple
  state but will need discrete methods for pile operations in a real card game

  ---
  Summary: Not quite ready. The setup gap means you'd need to write a Runner
  subclass before running anything real. The dead code and resume validation
  bypass are small and easy to fix. Everything else is either known or
  documentation work.
